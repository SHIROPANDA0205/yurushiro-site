# コードが公開されるまで

手元で書いたコードが https://yurushiroai.com に出るまでに、何がどこへ動いているのか。
2026年9月のサイト全面刷新（[PR #1](https://github.com/SHIROPANDA0205/yurushiro-site/pull/1)）を題材にしています。

> 図つきで読みやすい版はこちら → https://claude.ai/code/artifact/8cec6c0f-298a-4418-accf-93d6813ad772

## 1. 登場するのは3つの場所だけ

Gitが分かりにくいのは、コードが「いまどこにあるか」が見えないからです。場所は3つしかありません。

| 場所 | どこ | ここで何をするか |
| --- | --- | --- |
| **ローカル** | 自分のPCの中 | ファイルを編集する／`npm run dev` で確認する／変更を記録する（commit） |
| **GitHub** | インターネット上の保管庫 | 記録を送って保管する（push）／変更内容を確認する／本番に入れるか判断する（PR） |
| **本番サイト** | yurushiroai.com | Vercelが自動で作る。GitHubの `main` を見ていて、mainが変わると自動で更新される |

```
[ローカル] --push--> [GitHub] --merge--> [本番サイト]
   PCの中            保管庫だけ           公開される
```

### ここが要点

**Vercelは `main` ブランチだけを見ています。**

- `main` 以外のブランチにいくらpushしても、本番サイトは変わらない
- `main` が変わった瞬間に、自動で本番が更新される

作業用のブランチを切るのは、この性質を使って「まだ公開されない安全な場所」を作るためです。

## 2. 5つの言葉

| 言葉 | 意味 | 場所 |
| --- | --- | --- |
| **commit** | 変更に名前をつけて記録すること。セーブポイントを作る感覚。この時点ではまだ手元にしかない | ローカル |
| **branch** | 作業用に分けた「枝」。本線（`main`）を触らずに作業する場所。失敗しても本線は無傷 | ローカル → GitHub |
| **push** | 手元の記録をGitHubに送ること。PCが壊れても消えない状態になる。まだ公開ではない | ローカル → GitHub |
| **Pull Request（PR）** | 「この枝の変更を本線に入れていいか」という提案。一人で開発していても、公開前の最終確認の場として役立つ | GitHub |
| **merge** | PRを承認して本線へ取り込むこと。**ここが公開のスイッチ** | GitHub → 本番 |

## 3. 実際に起きたこと（サイト全面刷新のとき）

1. **ブランチを作った** — `redesign-ai-link-craft`。ここから先の作業はmainに一切影響しない
2. **変更を記録した（commit）** — 69ファイル分をひとつの記録に。記録番号 `515a195`。まだ手元だけ
3. **GitHubに送った（push）** — 作業内容は保管されたが、**本番サイトはまだ古いまま**
4. **PRを作った** — [PR #1](https://github.com/SHIROPANDA0205/yurushiro-site/pull/1) として提案を作成。ブラウザで操作
5. **マージした** — mainに取り込み（`c816295`）。**この瞬間が公開**
6. **Vercelが自動デプロイした** — mainの変化を検知してサイトを作り直し。操作不要

## 4. 次にやるときの手順

実績を1件足したい、文章を直したい——そういうときの流れです。

### ① 最新の状態から始める

前回の変更を手元に取り込んでから、新しい枝を作ります。

```bash
git checkout main
git pull
git checkout -b add-works-2   # 枝の名前は内容が分かるものを
```

### ② 編集して、手元で確認する

```bash
npm run dev   # http://localhost:3000 で確認
```

### ③ 記録して、GitHubへ送る

```bash
git add -A
git commit -m "本業の実績を1件追加"
git push -u origin add-works-2
```

### ④ GitHubでPRを作る

push後にターミナルへ表示されるURLを開くと、PR作成画面が開きます。
緑の **Create pull request** を押すだけです。

数分待つとVercelがコメントでプレビューURLを貼るので、公開前の姿を確認できます。

### ⑤ 問題なければマージ

**Merge pull request** を押した瞬間に公開されます。
ここだけは戻すのに手間がかかるので、押す前にプレビューを見る習慣をつけてください。

### 迷ったとき

```bash
git branch --show-current   # いまどの枝にいるか
git status                  # 何を変更したか
```

どちらも見るだけのコマンドなので、何度実行しても壊れません。

## 5. 公開したものを戻したいとき

「出したけどやっぱり戻したい」は普通に起きます。方法を知っておくだけで、マージのハードルが下がります。

**方法A：GitHubで打ち消す**
PR画面の **Revert** ボタンを押すと、「その変更を取り消す」PRが自動で作られます。
それをマージすれば元に戻ります。削除ではなく打ち消しなので、履歴は残り、あとからやり直せます。

**方法B：Vercelで表示だけ戻す**
Vercelの Deployments 画面から以前のデプロイを選び、**Promote to Production** を押します。
コードを触らずに表示だけ戻せるので、緊急時はこちらが早いです。

## 6. つまずいた箇所の記録

どちらも「失敗」ではなく、メッセージの読み方の問題でした。

### PRがコマンドで作れなかった

```
Resource not accessible by personal access token (createPullRequest)
```

- **原因**: GitHubのアクセストークンにPR作成の権限がなかった。pushはできるがPR作成はできない設定
- **対処**: ブラウザでPRを作れば問題ない。コマンドから作りたい場合は、トークン設定で「Pull requests」の権限を追加する

### Vercelの環境変数が登録できなかった

```
A variable with the name `NEXT_PUBLIC_FORMSPREE_ID` already exists
```

- **原因**: すでに登録済みだったため、同じ名前で二重に追加できなかっただけ。エラーに見えるが「すでにある」という報告
- **対処**: 何もする必要はなかった

なおその前に出ていた赤字は別件です。`NEXT_PUBLIC_` で始まる変数は仕組み上かならずブラウザに公開されるため、
Vercelが「Secret（秘密）ではなくConfigに分類してください」と促していたものでした。
